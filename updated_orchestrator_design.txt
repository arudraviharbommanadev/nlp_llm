UPDATED ORCHESTRATOR DESIGN FOR MULTI-MODEL STUDY ASSISTANT

1. PRODUCT GOAL

Build a multi-model study assistant that can:
- understand user questions deeply
- classify one or more intents
- break complex requests into sub-tasks
- route each sub-task to the most suitable model
- decide when retrieval is needed
- support conversational study workflows
- store, reload, export, and delete chat history per session
- present routing and progress clearly in the UI


2. CORE IMPROVEMENT OVER CURRENT IDEA

Your current prompt is a good router prompt, but it is still too minimal for a real orchestrator. A stronger design should:
- support multiple intents instead of only one
- distinguish simple vs complex queries
- detect when decomposition is necessary
- support UI-friendly outputs
- support database-friendly metadata
- include retrieval strategy, not just a yes/no flag
- include confidence and reasoning metadata for orchestration
- support session-level actions like save, reload, export, and delete
- prepare the system for future analytics and evaluation


3. UPDATED ORCHESTRATOR RESPONSIBILITIES

The orchestrator should:
- classify the user request
- identify primary and secondary intents
- determine whether the request is direct-answer, decomposition, or multi-stage
- decide whether internal knowledge is enough or RAG is needed
- build a task plan
- assign the best model for each task
- set execution priority
- return structured JSON only

5. MODEL ROUTING POLICY

Recommended model mapping:
- qwen2.5:
  use for coding, debugging, code explanation, API logic, implementation help
- mistral:
  use for explanations, tutoring, light reasoning, rewrite, compare, translation
- mixtral:
  use for long-context reasoning, multi-step decomposition, essay-length analysis, multi-document understanding
- flan-t5:
  use for structured quiz generation, short QA formatting, flashcards, schema-like outputs
- deepseek-r1:
  use for math, formal reasoning, derivation, step-by-step logic solving
- bart/pegasus:
  use for summarization, compression, notes-to-summary transformation

Routing rules:
- prefer the cheapest sufficient model
- use a single model when the query is simple
- decompose only when the task is clearly multi-intent or multi-step
- use mixtral only when deeper reasoning or long context is actually needed
- use RAG only when the answer depends on external or source-grounded knowledge


6. WHEN RAG SHOULD BE USED

Set `needs_rag = true` when:
- the user asks from uploaded notes, textbook material, slides, docs, or stored knowledge base
- the user asks for source-grounded answers
- the query is factual and likely needs external knowledge
- the user asks “from my notes”, “from this chapter”, “based on the document”, or similar
- the answer must cite evidence

Set `needs_rag = false` when:
- the task is generic coding
- the task is pure explanation from general knowledge
- the task is summarization of already supplied text
- the task is math solving from the prompt itself
- the task is translation or quiz generation from provided input

Recommended improvement:
- instead of only `needs_rag`, also output `rag_mode`
- possible values:
  `none`, `local_notes`, `web`, `hybrid`


7. IMPROVED OUTPUT JSON DESIGN

      "task_id": "task_1",

      "model": "mistral",
      "query": "Explain photosynthesis in simple terms for a class 10 student.",
      "priority": 1,
      "depends_on": []
    }
  ],

}

Why this is better:
- easier for backend orchestration
- easier for frontend progress display
- easier for debugging
- easier to save in the database


8. UPDATED MASTER ORCHESTRATOR PROMPT

Use this as the improved system prompt:

You are an AI Orchestrator Agent for a multi-model study assistant system.

Your responsibilities are to:
1. deeply understand the user's query
2. identify the primary and secondary intents
3. decide whether the request is simple, complex, or multi-intent
4. break the request into sub-tasks when necessary
5. assign the best available model for each task
6. decide whether retrieval is required
7. return ONLY valid JSON with no explanation

Available capabilities:
- coding
- explain
- quiz
- summarize
- math
- rag_search
- translate
- compare
- rewrite
- flashcards
- planning

Available models:
- qwen2.5: coding, debugging, implementation, code understanding
- mistral: explanation, tutoring, general reasoning, rewrite, compare, translation
- mixtral: deep reasoning, long context, complex decomposition
- flan-t5: structured quiz generation, flashcards, short QA
- deepseek-r1: math, equations, logic, step-by-step reasoning
- bart/pegasus: summarization and compression

Routing rules:
- always choose the most efficient model that can solve the task well
- decompose complex or multi-intent requests into multiple tasks
- use a single task for simple requests
- use retrieval only when the task needs source-grounded or external knowledge
- if retrieval is needed, include a rag_search task before answer-generation tasks
- if multiple tasks exist, order them by priority
- include dependencies when one task depends on another
- output valid JSON only

11. DELETE HISTORY PER CHAT

This should be added both in backend and UI.

Backend API addition
- add endpoint:
  `DELETE /sessions/{session_id}`

Behavior
- delete only the selected saved chat
- return success JSON
- if session does not exist, return 404

Recommended response
{
  "success": true,
  "deleted_session_id": 12
}

Frontend behavior
- each saved session card gets a delete icon/button
- clicking delete opens a confirmation modal
- after confirmation:
  call `DELETE /sessions/{session_id}`
- remove the deleted chat from sidebar immediately
- if the currently open saved session is deleted:
  clear it from the main panel and show a neutral state message

UX protection
- require confirmation before deletion
- use clear destructive styling
- optionally support undo for a few seconds later

13. BACKEND ARCHITECTURE DESIGN

Recommended backend flow:
1. receive user message
2. store user message in database
3. send user message to orchestrator
4. parse orchestrator JSON
5. if `needs_rag` is true, run retrieval step
6. execute each task in order of priority
7. aggregate outputs if needed
8. stream intermediate task updates to frontend
9. store assistant response plus orchestration metadata
10. return final response

Recommended modules
- `orchestrator.py`
  handles prompt, intent classification, decomposition, task planning
- `router.py`
  dispatches tasks to selected models
- `rag.py`
  retrieval logic for notes/docs/web
- `executor.py`
  executes multi-step plans and handles dependencies
- `database.py`
  stores sessions, messages, orchestrator traces
- `main.py`
  FastAPI endpoints and streaming


14. STREAMING DESIGN

For a better UI, stream stages like this:
- intake
- orchestration
- retrieval
- task_execution
- aggregation
- final_response

Each event should include:
- stage id

This makes the UI much more understandable than only showing one final model.
